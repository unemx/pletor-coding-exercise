ADR-002

Image delivery and thumbnail strategy.

Gallery cards should receive images sized for their rendered dimensions, not the original high-resolution uploads.

Context

Loading a 4000px original image into a small card wastes bandwidth, delays the largest visible images, and makes Slow 4G testing look worse than the actual UI needs to be. The gallery needs a predictable way to request assets that match display size and density.

The current dataset also changes the shape of the decision. Seeded images are already delivered from Unsplash-style URLs that support width, height, crop, quality, and format parameters. User uploads, however, are stored as local static files. Treating both sources as if FastAPI should proxy every thumbnail would add a hot image-serving path that is too expensive for a 90-minute, zero-budget exercise and would duplicate work the existing remote image URLs can already do.

Thumbnail URLs also do not remove the need for paginated metadata. Returning 2000 image records at once is manageable in a demo, but it scales poorly and competes with rendering work during the initial load. The delivery contract should let the gallery request images incrementally as the user scrolls.

Decision

Use a zero-budget paginated thumbnail strategy: expose a backend-owned image delivery contract with cursored metadata, original URLs, thumbnail URLs, intrinsic dimensions, and optional low-quality placeholders, while avoiding extra infrastructure or uncached per-request transforms.

Gallery metadata should expose intrinsic width, height, original_url, a card-sized thumbnail_url, and optionally a placeholder_hash with a placeholder_type such as thumbhash or blurhash. For seeded remote images, the API can derive thumbnail URLs by adjusting the existing width, height, crop, quality, and format parameters instead of proxying the image. For local uploads, the backend should inspect the original dimensions and persist a small bounded thumbnail variant during upload. Original assets remain the source of truth, while thumbnails are optimized delivery artifacts.

The frontend should render the thumbnail URL in gallery cards, provide srcset and sizes when multiple densities are available, and reserve aspect-ratio space from the returned dimensions before the image loads. When a placeholder hash exists, the card can show a ThumbHash or BlurHash preview while the thumbnail loads; this improves perceived quality but does not replace the thumbnail. Full-size views can still use the original URL.

Consequences

  • Positive: fewer bytes are downloaded during initial gallery rendering.
  • Positive: LCP improves because visible images are closer to their display size.
  • Positive: thumbnails reduce memory pressure when scrolling a large collection.
  • Positive: dimensions in the API contract let the layout avoid post-load shifts.
  • Positive: pagination keeps initial metadata, reconciliation, and render work bounded.
  • Positive: ThumbHash or BlurHash placeholders make lazy-loaded cards feel intentional instead of blank.
  • Positive: the plan fits the exercise constraints without buying or configuring extra infrastructure.
  • Tradeoff: uploaded files need dimension extraction and thumbnail generation at ingest time, ideally with a small library such as Pillow.
  • Tradeoff: placeholder hashes need generation and decoding code, so they should remain secondary to dimensions and thumbnails.
  • Tradeoff: the image schema needs to distinguish original delivery URLs from optimized gallery URLs.

Implementation Notes

  • Change the list endpoint from returning every image to a paginated response, such as GET /images?limit=50&cursor=... with a stable next_cursor.
  • Store or return width and height for every image record.
  • Return both original_url and thumbnail_url from the gallery API.
  • For seeded remote images, derive thumbnail URLs from known URL parameters such as width, height, crop, format, and quality.
  • For uploaded local files, generate a narrow set of persisted variants, such as a 400px card thumbnail and an 800px high-density thumbnail.
  • Prefer ThumbHash for uploaded-image placeholders if a small implementation is available; otherwise use BlurHash or fall back to a neutral skeleton. Do not block the thumbnail work on placeholders.
  • Avoid on-demand per-request image transforms for the main gallery unless a local disk cache is implemented.

Postmortem

Trace analysis showed that third-party image delivery was a risk but not the only LCP issue. Once the app was measured in production mode, the LCP candidate was a local thumbnail and loaded in well under a second; the remaining delay came mostly from when the SPA discovered and rendered that image.

The final implementation keeps the backend-owned contract and adds a pragmatic disk cache for seeded remote thumbnails under /uploads/remote-thumbnails. The first visible records are warmed before the initial gallery response, and the rest of the page is warmed in the background. Remote URLs remain the source of truth and the fallback path, so a cache miss or failed upstream image does not break the gallery.

ThumbHash remains a perceived-performance enhancement rather than an LCP fix. It can make unloaded cards feel intentional, but Chrome still reports LCP when the final image paints. Similarly, a static preload manifest is useful only when kept small: over-preloading first page thumbnails can compete with the actual LCP image on Slow 4G.

Alternatives Considered

Frontend-Only Resizing

CSS can make an original image look smaller, but it cannot avoid downloading and decoding the oversized asset. This does not solve the performance bottleneck.

Backend Transform Proxy for Every Image

A single /thumbnail endpoint is tempting because it hides provider details from the frontend. In this codebase it would make FastAPI responsible for downloading, decoding, resizing, encoding, caching, and streaming every visible gallery image. Without a persistent transform cache, that shifts the bottleneck from the browser to the API and is worse than using the existing upstream image service for seeded assets.

Use Upstream Image Parameters Only

This is efficient for the seeded dataset because those images already support size and quality parameters. It is incomplete for user uploads, which are local static files and need dimensions plus generated variants to avoid regressing after upload.

Fetch All Metadata Up Front

Returning every image record keeps the API simple, but it delays first render and forces the client to reconcile data the user may never scroll to. A small cursor-based page size keeps initial load bounded while still working with virtualization and scroll restoration.

Placeholder Hashes Instead of Thumbnails

ThumbHash and BlurHash are useful for perceived loading quality, especially with mixed aspect ratios, but they are not image delivery. They avoid blank cards while thumbnails load; they do not reduce the bytes or decode cost of the final image.

Pre-generate Every Possible Size

Pre-generation is production-friendly at scale, but every possible size is heavier than needed for this exercise. A bounded set of gallery variants is enough to demonstrate the delivery strategy without extra infrastructure.

The challenged version of this ADR is narrower than the base decision: the backend owns the contract, metadata, and upload thumbnails, but the implementation should stay local, cheap, and achievable inside the exercise window.
