ADR-003

Resilient batch upload architecture.

Uploading a shoot should feel trustworthy: users need progress, partial failure recovery, cancellation, and a responsive UI while files are in flight.

Context

The MVP upload flow handles files one at a time, which does not match how creative teams work after a shoot. Batch upload needs to tolerate slow networks, individual failures, and user actions without blocking the rest of the application.

Decision

Use Uppy as the upload orchestration layer, configured with XHRUpload, Golden Retriever, bounded concurrency, image restrictions, per-file progress, cancellation, retry behavior, and the existing FastAPI upload endpoint.

The 90-minute exercise rewards production judgement over rebuilding commodity browser upload mechanics. Uppy provides the queue, drag-and-drop UI, per-file lifecycle, and upload progress events that fetch does not expose. Golden Retriever adds best-effort browser-side recovery for selected files after a refresh or crash. The app should still keep Uppy behind an upload feature boundary so the rest of the codebase depends on our upload component rather than scattered plugin configuration.

Consequences

  • Positive: mature upload behavior can be delivered inside the take-home timebox.
  • Positive: one failed file does not invalidate the full batch.
  • Positive: XHRUpload gives real per-file progress and cancellation against the current API.
  • Positive: Golden Retriever can recover queued files and Uppy state after a tab refresh.
  • Positive: concurrency limits protect both the browser and backend from avoidable pressure.
  • Tradeoff: Uppy adds a dependency and hides some queue internals behind plugin APIs.
  • Tradeoff: recovered in-flight uploads restart instead of resuming from the last byte with the current API.
  • Tradeoff: production-safe retries still require idempotency keys or true resumable upload support.

Alternatives Considered

Custom Managed Queue

A custom queue would make the state machine explicit and avoid a dependency, but it spends limited exercise time recreating drag-and-drop, progress, cancellation, retry, and error UI that Uppy already handles well.

Single Request for the Whole Batch

Sending every file as one request is simpler, but progress, retry, and cancellation become coarse-grained. One failure risks forcing the user to start over.

Unlimited Parallel Uploads

Uploading every file at once can look fast on a small local dataset, but it becomes noisy and unreliable under realistic network constraints. A bounded queue is more predictable.

Golden Retriever helps satisfy the refresh-survival bonus without backend changes, but it is not a substitute for resumable uploads. True byte-level resume would require a protocol such as Tus or multipart uploads with matching backend support.
