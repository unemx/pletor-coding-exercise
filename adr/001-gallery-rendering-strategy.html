ADR-001

Gallery rendering strategy.

The gallery must stay smooth with thousands of mixed-ratio images, including on a slow network and under CPU throttling.

Context

The seeded database contains around 2000 images with mixed aspect ratios. Rendering every image in the DOM creates unnecessary layout work, memory pressure, network contention, and janky scrolling. A fixed-size grid would be simpler, but it would crop or distort the visual rhythm of the gallery and would not match the product expectation for creative assets.

Decision

Use react-photo-album as the first implementation choice for a responsive mixed-ratio gallery, defaulting to its justified rows layout and pairing it with paginated thumbnail delivery.

The main risk in this exercise is not writing card markup; it is getting mixed aspect ratios, responsive sizing, stable image boxes, and scroll behavior right inside a short implementation window. A focused photo-layout library is safer than hand-rolling justified row math or wiring a low-level virtualizer from scratch.

The gallery should use known image dimensions, thumbnail URLs, and responsive srcset/sizes data from the API. Cards keep stable dimensions before the asset loads, so scrolling does not trigger cumulative layout shift. Scroll restoration is treated as part of the gallery state rather than a side effect of browser history.

Library Comparison

Option Strengths Risks Fit for this exercise
react-photo-album Purpose-built for responsive photo galleries, supports rows, masonry, dimensions, responsive images, and infinite scroll helpers. Its offscreen optimization is not the same as strict DOM virtualization, so memory must be verified with profiling. Chosen. Best balance of visual quality, implementation speed, and explainable tradeoffs for a 90-minute test.
masonic Purpose-built virtualized masonry with strong large-list behavior. Masonry is less predictable for scroll restoration and row-level layout stability than justified rows. Good fallback if profiling proves strict virtualization matters more than justified layout quality.
react-virtuoso Mature virtualization primitives with dynamic height support and good ergonomics. More generic; still requires custom gallery layout work for a polished mixed-ratio photo grid. Strong fallback for list/grid virtualization, but less directly aligned with the visual gallery requirement.
@tanstack/react-virtual Excellent low-level virtualizer with high control and small surface area. Requires more custom measurement, layout, and restoration code. Too low-level for the available time unless the library choices above fail.
react-window Small, familiar, and effective for fixed-size or simple variable-size lists. Awkward for responsive mixed-height gallery layouts and no longer the strongest default choice. Not selected because it pushes too much gallery-specific complexity into app code.
Custom implementation Maximum control over row computation, overscan, and restoration. Highest delivery risk; easy to under-build measurement, resize, and edge-case behavior. Rejected for this test. The time is better spent integrating thumbnails, metadata, and measurement.

Consequences

  • Positive: layout quality comes from a library designed specifically for photo galleries.
  • Positive: implementation time stays focused on API metadata, thumbnails, scroll restoration, and measurement.
  • Positive: justified rows give a polished mixed-ratio layout without cropping every asset into a fixed card.
  • Tradeoff: the selected library must be profiled because offscreen optimization may not provide strict DOM bounds.
  • Fallback: if memory grows unacceptably after scrolling the full dataset, switch to masonic or react-virtuoso.

Alternatives Considered

Use a Strict Virtualization Library First

Libraries such as masonic, react-virtuoso, and @tanstack/react-virtual provide stronger virtualization guarantees, but they leave more layout responsibility in the application. They are better fallback choices than first choices for a short exercise where visual layout quality is also a core requirement.

Render the Full List

This is the simplest implementation, but it fails the core performance requirement and does not leave enough headroom for larger customer workspaces.

Use a Fixed-Size Grid

A fixed grid is easier to virtualize, but it ignores the mixed aspect ratios that matter in a visual product. It would make the demo feel less like a production gallery.
