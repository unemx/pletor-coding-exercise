ADR-004

Feature-oriented folder structure.

The exercise asks for production judgement, so the code should be easy to review and extend without introducing a large application framework.

Context

The original MVP is intentionally small, but the requested work adds distinct concerns: gallery rendering, upload queue management, API access, reusable UI, and shared types. Leaving everything in one file makes the result harder to reason about during review.

Decision

Organize the frontend by feature boundaries, with shared infrastructure extracted only when more than one feature needs it.

Gallery-specific components, hooks, and helpers should live near the gallery feature. Upload-specific queue logic should live near the upload feature. API clients, shared UI primitives, and shared types should sit in common folders because they represent cross-cutting contracts.

Target Shape

  • features/gallery owns virtualized gallery UI, layout helpers, and scroll restoration.
  • features/upload owns drag-and-drop UI, queue state, retry behavior, and upload controls.
  • lib/api owns typed calls to the backend and keeps transport details out of components.
  • components/ui contains small reusable presentational pieces used across features.
  • types contains shared contracts when they are used by more than one feature.

Consequences

  • Positive: reviewers can inspect gallery and upload decisions independently.
  • Positive: stateful business logic is kept close to the UI that uses it.
  • Positive: shared folders stay small because code is promoted there only when reused.
  • Tradeoff: feature folders can duplicate small patterns before an abstraction is justified.

Alternatives Considered

Layer-Only Structure

Splitting everything into global components, hooks, and utils folders is familiar, but it hides ownership as the app grows.

Full Domain Architecture

A stricter domain architecture would be excessive for a take-home. The selected structure keeps clear boundaries without making simple changes feel ceremonial.
